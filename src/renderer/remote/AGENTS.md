# Remote Console phone UI

`src/renderer/remote/` (#254): a SECOND Vite entry (`remote/index.html`), served by main's console server out of `dist/renderer` — never loaded by the desktop window. It imports only React, `@xterm/xterm`, `src/shared/*`, `utils/touch-pan.ts`/`touch-fling.ts` and its own `remote/i18n` (no store, no desktop i18n, no components — a test enforces the graph). Anything BOTH entries import (React, xterm, `src/shared/*`, the touch recognisers) is split by Vite into a separate shared chunk that the desktop window loads too — which is why a fix marker in a shared module is not in `index-*.js` (see "Check that a fix shipped" in the `wmux-release` skill). The manifest is emitted as `dist/renderer/remote-manifest.json` (NOT `.vite/`: a dot directory is not guaranteed into the asar), and the server serves only the manifest closure of `remote/index.html`. `npm run dev` does not serve it: run `npx vite build --watch` in a second pane; until the first build the console reports `ui-not-built`. The grid is the desktop's and `fit.ts` picks the font from the WIDTH alone, so the grid can be TALLER than the phone's box — and the box clipped the bottom rows, where an agent keeps its input line (#265, reported as "the buttons hide the line below"; the buttons were never over it). `vertical-clip.ts` makes the box a window over the grid, pinned to the bottom across layout changes (the keyboard opening), moved through `wrap.scrollTop`; a finger treats grid and scrollback as one document. The key bar's ORDER is a feature (#266): the row scrolls, so only its first keys exist for someone who has not found that out — Enter was eighth of seven visible, and with a blocked agent and an empty box the composer button was a disabled Insert. It is now the key bar's Enter (same frame, same arming, same server guards — a second place to press it, not a second way to answer). The mirror is read-only xterm (`disableStdin`, no `onData`, no clipboard/OSC 52, no resize or wheel messages); the snapshot comes from the desktop renderer that hosts the surface, over `REMOTE_RENDERER_REQUEST` on the SAME webContents its PTY_DATA goes to, which is what orders the snapshot against the stream
