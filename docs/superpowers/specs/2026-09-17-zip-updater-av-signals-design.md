# Zip Updater: Fewer AV Behavioural Signals — Design Spec

**Date:** 2026-09-17
**Status:** Implemented on 2026-09-17 (tasks 1–5). Verification results recorded under §5 Definition of done; F12 and D11 were found during that verification and added to the scope
**Issue:** mkh63d/wmux#3 · **PR:** mkh63d/wmux#2 (extends it)

> Cut the apply-update helper down to what it actually needs to do — wait, copy, relaunch — so a portable-zip update stops looking like a dropper to behavioural antivirus engines, without leaking files into `%TEMP%`.

## 1. Overview

Issue #3 reports a full system freeze (Task Manager unreachable, hard reset needed) when Norton's real-time protection reacts to a portable-zip self-update. PR #2 removed the helper's `del "%~f0"` self-delete. That removes one signal, but leaves a stronger one in place (a hidden PowerShell recursively stripping Mark of the Web) and turns the self-delete into an unbounded leak of `.cmd` files in `%TEMP%`.

This spec does not promise to fix the Norton freeze. wmux.exe is unsigned, and a new, low-prevalence unsigned binary will draw a reputation scan whatever the helper looks like. The goal is to remove every signal the helper emits that buys wmux nothing, and to make sure that an antivirus getting in the way of an update leaves the user with a running wmux.

## 2. Current State

The helper is generated by `buildApplyUpdateCmd()` (`src/main/zip-updater.ts`) and started detached, hidden, by `applyStagedPortableUpdate()`.

| Step | Helper line(s) | Needed? |
|---|---|---|
| Wait for old PID | `timeout` + `tasklist \| findstr` loop, 1 s | Yes (cannot overwrite a running exe) |
| Copy payload | `robocopy "%SRC%" "%DST%" … /R:5 /W:1` | Yes |
| Strip MOTW | hidden `powershell.exe … Get-ChildItem -Recurse \| Unblock-File` | See §3 |
| Relaunch | `start "" "%EXE%"` (unconditional) | Yes |
| Remove payload | `rmdir /s /q "%SRC%"` | Yes, but incomplete — see §3 |
| Self-delete | `del "%~f0"` — **removed by PR #2** | — |

Files the update flow creates in `os.tmpdir()`:

| Path | Created by | Removed by |
|---|---|---|
| `wmux-update-<ver>-<pid>.zip` | `runPortableZipUpdate` | same function, on success and failure |
| `wmux-update-<ver>-<pid>\` | `runPortableZipUpdate` | on failure: same function; on success: helper `rmdir "%SRC%"` |
| `wmux-apply-update-<pid>.cmd` | `applyStagedPortableUpdate` | nothing, since PR #2 |

All three names carry the same `<pid>`: `process.pid` of the wmux that downloaded and applied the update.

## 3. Established Facts

Verified by reading the code on 2026-09-17, not by running an update.

- **F1 — the downloaded zip carries no MOTW.** It is fetched with Electron `net.request` and written with `fs.createWriteStream`; neither writes a `:Zone.Identifier` stream. The extracted payload therefore has none either.
- **F2 — wmux already strips MOTW in-process on every launch.** `stripMotw()` (`src/main/index.ts:399`, called at `:739`) unlinks `:Zone.Identifier` from every `.exe/.dll/.node/.lnk` under the install dir. It runs inside the new wmux, so it cannot help the relaunch that starts it: `start` goes through ShellExecute, which is where Windows checks MOTW, before any wmux code runs.
- **F3 — the PowerShell shim strips its own files.** `powershell-shim.ts:82`. Shell integration runs with `-ExecutionPolicy Bypass` (`pty-manager.ts:378`), so MOTW on it does not block anything.
- **F4 — `rmdir "%SRC%"` leaves a directory behind only for a zip that wraps a top-level folder**, which no official release does. `findPayloadRoot` returns the inner folder in that case, so the outer `wmux-update-<ver>-<pid>\` would survive, empty. But both release paths zip the *contents* of the build dir (`release.yml:197` `Compress-Archive -Path "release/win-unpacked/*"`, and the manual `wmux-release-staging\*`), and the v2.12.0 asset confirms it: its central directory (read 2026-09-17) has `wmux.exe`, `resources/`, `locales/` at the root. For real updates `SRC` *is* the extract dir and `rmdir` removes all of it. What does leak in practice is the extract dir when `rmdir` itself fails part-way, e.g. on a file an antivirus is still scanning. Plausible on exactly the machines #3 is about, not verified.
- **F5 — the helper name contains the PID**, so without a delete one new `.cmd` accumulates per update.
- **F6 — `%TEMP%` is not reclaimed automatically** unless Storage Sense is enabled. PR #2's comment says otherwise.
- **F7 — a staged update can sit in `%TEMP%` indefinitely while wmux runs.** `promptToInstall` (`updater.ts:301`) offers *Later*; the extracted payload stays in `stagedZip` and is applied on a later badge click (`updater.ts:213`), possibly days after it was extracted.
- **F8 — a missing payload leaves the user with no wmux.** `applyStagedPortableUpdate` calls `app.quit()` without checking the payload, and the helper's `if not exist "%SRC%\wmux.exe" exit /b 1` runs *before* `:relaunch`. Anything that deletes a staged payload (Storage Sense, a manual temp cleanup, or a careless sweep) turns the next *Install and restart* into a quit with no restart. Pre-existing, but a sweep adds one more way to reach it.
- **F9 — a helper that never starts also leaves the user with no wmux.** `applyStagedPortableUpdate` calls `spawn()` and then `app.quit()` straight away, with no `'error'` listener on the child. A launch failure (an antivirus blocking `cmd.exe` from a hidden detached parent) arrives asynchronously as an `'error'` event, after the quit has already started, and with no listener it is also an uncaught exception in main. A `writeFileSync` that throws on the helper (an antivirus blocking `.cmd` writes to `%TEMP%`) is synchronous, but from the badge path (`updater.ts:214`, inside `setImmediate`) it is uncaught too.
- **F10 — the extract dir's age says nothing about whether a helper is using it.** Its `mtime` is set when the extraction finished. After *Later* (F7) that can be days before *Install and restart*, and by the time the helper copies from it the PID in its name belongs to a wmux that has exited. The helper `.cmd` is the only leftover whose `mtime` is set at apply time.
- **F11 — `installPrompted` survives a failed install.** `promptToInstall` (`updater.ts:303`) sets it and clears it only on *Later*. Today that does not matter, because *Install and restart* always quits. Once an install can fail without quitting, the next downloaded update would never show its dialog.

Found while verifying the implementation (task 5), by running the helper rather than reading it:

- **F12 — the helper never runs when `%TEMP%` contains a space.** `spawn(cmd, ['/d', '/c', helper, …])` lets Node quote each argument. With a space in the helper path (any account named "First Last") the command line starts with a quote and holds more than two, so `cmd /c` strips the first and the last quote and runs `C:\Users\First`. Reproduced with a real `child_process.spawn`: exit 1, `'…\Jan' is not recognized`. wmux has already quit, and `cmd.exe` itself started, so the `'spawn'` guard of US-3 cannot see it.
- **F13 — `timeout.exe` refuses the helper's stdin.** The helper is spawned with `stdio: 'ignore'`, and `timeout /t N` then exits at once with `ERROR: Input redirection is not supported`. The wait loop therefore re-runs `tasklist | findstr` back to back instead of once a second, and the 2 s pause before robocopy does not happen (robocopy's `/R:5 /W:1` still covers a file that is briefly locked). Measured: `timeout /t 3` with NUL stdin returns in 66 ms, and an 8 s wait costs 0.31 s of CPU with the error line repeated to the console. _Fixed under D12._

Found while testing the built copy manually (T1 on a portable test install), by a user rather than by the code:

- **F14 — the helper's console is visible, and says nothing.** `applyStagedPortableUpdate` passes `windowsHide: true`, which does nothing here: `detached: true` implies DETACHED_PROCESS, Windows ignores CREATE_NO_WINDOW beside it, and cmd.exe allocates a console of its own. Measured — a detached spawn adds one `conhost.exe`, an otherwise identical non-detached one adds none. The window that appears is empty apart from F13's repeated error, and Windows titles a console after the child running in it, so it reads `C:\WINDOWS\System32\findstr.exe /I /C:" 39944 "`. Reported as: *"the terminal window does not close right away… I did not know whether to close it or type something"*.
- **F15 — dropping `detached` is not available as a fix.** In the same probe, a non-detached child died with its parent: 0 of 10 loop iterations when the parent exited immediately, 10 of 10 when it stayed alive. The measurement was taken inside a job object (both the shell and every `wmux.exe` on the machine report `IsProcessInJob` true), so it does not settle what happens on an arbitrary install — which is the point: the helper outliving wmux is the one thing it must do, and wmux has already quit when it is wrong.

## 4. Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| D1 | Hidden `Unblock-File` step | **Remove entirely** | F1–F3: it strips nothing the update wrote, and executables are already covered in-process. It is the helper's strongest AV signal (MITRE T1553.005, MOTW bypass) for no gain. |
| D2 | `%TEMP%` leftovers | **Sweep on startup** | Bounds the leak PR #2 introduced (F5), also fixes F4 and debris from interrupted updates. Cleanup happens long after the helper exits, from wmux's own process, so it reads nothing like self-cleanup. |
| D3 | `tasklist \| findstr` wait loop | **Out of scope** | Its AV impact is speculation, and plain cmd has no quieter way to wait on a PID. Follow-up. |
| D4 | Delivery | **Extend PR #2** | New commits on `fix/updater-no-self-delete`; this spec is committed with the code; `Closes #3` becomes `Refs #3`, since nothing here is verified against Norton. |
| D12 | The visible helper console (F14) | **Keep it visible, make it explain itself; fix the wait with `waitfor`** | Hiding it needs `detached` gone, and F15 says that risks the helper dying with wmux — the one failure with no way back. A hidden detached script overwriting an unsigned exe is also the dropper shape this PR is reducing, so the window is the honest signal. It therefore sets a `title`, re-set inside the loop because Windows renames a console after its current child, and prints what it is doing in English. The pause becomes `waitfor /t N <name>`, which honours a NUL stdin (2.1 s measured for `/t 2`); not `ping -n`, the batch-sleep idiom of droppers. Where `waitfor.exe` is missing the loop degrades to the spin it already had. |
| D5 | Should the helper also remove the outer extract dir (F4)? | **No — helper unchanged beyond D1; the sweep covers it** | F4 cannot happen with an official zip. The real leak, a `rmdir` that fails on a locked file, would hit the same lock inside the helper. Changing a script that runs after wmux has quit adds risk for no gain. |
| D6 | When is a leftover safe to remove? | **Age > 1 h AND the PID in its name is not alive AND, for a zip or extract dir, no helper with the same PID is 1 h old or younger** | Age protects the helper `.cmd` while it runs (cmd reads a batch file line by line, so deleting it mid-run skips its `rmdir`). Age does *not* protect the extract dir (F10), so a fresh helper with the same PID protects its siblings: that `.cmd` was written at apply time, and all three names share the PID. The PID check protects a payload staged behind *Later* in a running wmux (F7), whatever its age. Every uncertain answer (PID reused, `EPERM`, negative age, unreadable helper) keeps the entry. |
| D7 | Fix F8 and F9 in this PR? | **Yes — check the payload, and quit only once the helper has started** | A sweep adds one more way for a staged payload to vanish, and F9 is the failure mode most likely on the machines #3 is about. Both fixes are a few lines and remove the no-restart outcome for every failure wmux can observe. |
| D8 | Where does the sweep live? | **`zip-updater.ts`, called from `index.ts`** | The names are created there, so one definition serves both creation and sweep and they cannot drift. `initAutoUpdater()` is ruled out: it returns early under `WMUX_DISABLE_UPDATER` and on zip installs, which contradicts US-2.1. |
| D9 | After a failed install, keep the staged payload? | **Keep it unless the payload itself is gone** | If only the helper failed to write or start, the payload is fine and a retry costs nothing; throwing it away forces another 100 MB+ download that fixes nothing. A missing payload is the one case where downloading again is the only way forward. |
| D10 | When does the sweep run? | **About 60 s after startup** | The update helper runs `rmdir "%SRC%"` right after starting the new wmux; a sweep at `whenReady` would race it on the same directory. The delay also keeps the sweep's I/O out of the startup window (#176). A wmux quit within the first minute simply does not sweep that run. |
| D11 | Fix F12 in this PR? | **Yes — `cmd /d /s /c ""<helper>" "<arg>" …"` with `windowsVerbatimArguments`** | It is the no-restart outcome US-3 exists to remove, on a path wmux cannot observe, and the fix is one pure function. `/s` makes cmd strip exactly the outer pair. A Windows path cannot contain `"`, and an argument that does is refused rather than allowed to re-split the line. Separate commit, so it can be dropped on its own. |

## 5. Requirements (Phase 1)

### Terminology

- **Helper** — the `.cmd` script generated by `buildApplyUpdateCmd()` and run detached by `applyStagedPortableUpdate()`.
- **Update leftover** — a file or directory in `os.tmpdir()` created by the portable-zip update flow (§2, second table).
- **Sweep** — the delayed startup pass that removes update leftovers.
- **Age** — `now − mtime` of the entry, where `mtime` is the last time the update flow wrote to it (for a directory: when a direct child was last added or removed). A negative age, from a clock moved backwards, counts as fresh. `mtime` rather than `birthtime`, because the extract dir is created *before* the download starts (`zip-updater.ts:311`), so its creation time can predate the extraction by the whole download.
- **Fresh helper** — a leftover matching the helper pattern whose age is 1 hour or less, or whose age cannot be read.

### US-1 — The helper does only what the update needs

**User story:** As a wmux user with behavioural antivirus, I want the update helper to avoid actions that look like malware, so that updating is less likely to trigger a lockdown.

**Acceptance criteria:**

1. The generated helper SHALL NOT invoke `powershell.exe` and SHALL NOT contain `Unblock-File`.
2. The generated helper SHALL NOT delete its own file.
3. The generated helper SHALL still wait for the old PID, copy the payload, relaunch `%EXE%` unconditionally (including after a robocopy failure), and remove the payload directory.

### US-2 — Updates do not leave debris behind

**User story:** As a wmux user who updates often, I want old update files cleaned up, so that `%TEMP%` does not fill with wmux scripts and empty folders.

**Acceptance criteria:**

1. WHEN a packaged wmux starts on Windows THEN it SHALL sweep update leftovers — regardless of install type (zip or NSIS) and regardless of `WMUX_DISABLE_UPDATER`.
2. WHEN wmux runs unpackaged (`npm run dev`) THEN it SHALL NOT sweep.
3. The sweep SHALL start about 60 seconds after startup, not during it, and SHALL NOT keep wmux from quitting.
4. An update leftover is exactly one of: a file `wmux-apply-update-<pid>.cmd`, a directory `wmux-update-<version>-<pid>`, or a file `wmux-update-<version>-<pid>.zip`, where `<pid>` is a positive integer no larger than 2³²−1. The sweep SHALL NOT remove any entry whose name does not match one of these patterns exactly, nor an entry whose type (file vs directory) does not match its pattern.
5. The sweep SHALL NOT remove a leftover whose age is 1 hour or less, or negative, since a helper may still be running.
6. The sweep SHALL NOT remove an extract dir or zip while a fresh helper with the same PID exists, since that helper may still be copying from it.
7. The sweep SHALL NOT remove a leftover whose embedded PID belongs to a live process, or whose liveness cannot be determined, since a running wmux may hold it as a staged update.
8. The sweep SHALL NOT follow or remove symbolic links or junctions.
9. IF removing an entry fails THEN the sweep SHALL skip it, log it, and continue; startup SHALL NOT fail or wait on the sweep.
10. WHEN the sweep removed or failed to remove anything THEN it SHALL write one line to `main.log` (not only the console, which a packaged build does not show), with the counts and the distinct error codes of the failures.

### US-3 — Installing an update never strands the user

**User story:** As a wmux user who clicked *Later* and came back days afterwards, or whose antivirus interferes with the update, I want *Install and restart* to fail safely, so that I am never left with wmux closed and nothing to restart it.

**Acceptance criteria:**

1. WHEN an install is confirmed AND `<payload>\wmux.exe` does not exist THEN wmux SHALL NOT write or start the helper and SHALL NOT quit. The updater state SHALL become `error` with a message saying the update must be downloaded again, and the staged update SHALL be forgotten, so the next badge click downloads it afresh.
2. WHEN the helper cannot be written, or the helper process fails to start, THEN wmux SHALL NOT quit. The updater state SHALL become `error` with the failure's message, and the staged update SHALL be kept, so the next badge click retries the install without downloading again.
3. wmux SHALL quit into an update only after the helper process has started (Node's `'spawn'` event).
4. WHEN an install fails without quitting THEN the next staged update SHALL show its install dialog as usual.

### US-4 — The code and the PR say what is true

**User story:** As a wmux maintainer, I want the comments and the PR to describe what the updater really does, so that nobody reintroduces a step or closes the issue on a guess.

**Acceptance criteria:**

1. Comments in `zip-updater.ts` SHALL NOT claim Windows reclaims `%TEMP%` on its own, and the header comment SHALL no longer list a MOTW step.
2. The PR description SHALL reference issue #3 without closing it.

### Definition of done

- `npm test`, `npm run lint` and `npm run build:main` pass.
- The generated helper is run by hand against a fake install dir in a scratch directory: it waits for a dummy PID, copies, relaunches, and removes the payload.
- A1 is checked in the same run (copy over an `.exe` carrying `:Zone.Identifier`, inspect the result, launch it with `start`) and its outcome recorded here.

**Results (2026-09-17, Windows 11 Pro 26200):**

- `npm run build:main` passes. `npm run lint` reports nothing in the changed files; its 14 errors are in files this change does not touch. `npm test`: 3061 passed, 10 failed in `pty-manager`, `cli-bin-shims`, `pipe-client-latency` and `wmux-bridge-transport` — the same 10 fail on the base commit `0614402`, so none come from this change.
- Helper run by hand, generated from the compiled `dist/main/zip-updater.js`, against a scratch install dir whose name contains a space: it waited for a dummy `ping` PID (exited at 3.3 s, relaunch seen at 5.3 s), copied the payload including a subdirectory, started `%DST%\wmux.exe`, removed the payload dir, and left its own `.cmd` on disk. The generated script contains no `powershell` and no `Unblock-File`.
- **A1 holds.** An old `wmux.exe` carrying `:Zone.Identifier` (ZoneId=3) was overwritten by robocopy with the helper's flags: the result has only `:$DATA`. Robocopy replaces the destination's streams, so the relaunched exe carries no MOTW and `start` has nothing to warn about. No security prompt appeared on the relaunch.
- Running the same helper through a real `child_process.spawn` surfaced F12 and F13 (§3).

**Results of D12 (2026-09-17, same machine, after two manual T1 runs on a portable test install):**

- The helper generated from the rebuilt `dist/main/zip-updater.js` was run against a dummy PID with stdin from NUL: it waited 6 s for that PID, paused 2 s, copied, relaunched (marker file written) and removed the payload — 8.4 s total at **0 s CPU**, with an empty stderr. The same script with F13's `timeout.exe` restored costs **0.31 s CPU** over the same run and prints `ERROR: Input redirection is not supported` to the console.
- Console output is the four English lines the window now shows: what is installing, that it closes by itself and wants no input, that it is waiting for wmux, then copying and starting.
- Not verified: how the title behaves in the real detached console during an update. `title` is re-set before each child for that reason, but the fix for F14's title was reasoned from Windows' renaming behaviour rather than measured in place.

### Out of scope

- Replacing the `tasklist | findstr` wait loop with a quieter way to wait on a PID (D3). Its pause is fixed under D12; the polling shape is unchanged.
- The hidden `powershell.exe -Command Expand-Archive` fallback in `extractZip`. It runs in wmux's own process, only when `tar.exe` fails, and is a far weaker signal than `Unblock-File`. Noted so it is not mistaken for an oversight; a follow-up if #3 persists.
- An antivirus that deletes or quarantines the helper `.cmd` after `cmd.exe` has started. wmux has already quit and cannot observe it.
- Code signing.
- Replacing the helper with an in-process rename-and-relaunch update.
- Verifying the fix against Norton — not available locally.
- The NSIS updater path.

### Constraints

- No new runtime dependencies; System32 tools and Node `fs` only.
- Must not add synchronous work to the startup path (the concern behind #176).

### Assumptions

- **A1** — _(Verified, see Definition of done.)_ Removing `Unblock-File` changes nothing the user can see. Non-executable files never needed it (F1, F3). `wmux.exe` carries no MOTW when the helper relaunches it: the new copy comes from `net.request` (F1), and the old copy was already stripped by `stripMotw()` when that version launched (F2). This rests on the *previous* launch's strip, since the relaunch happens before the new wmux runs any code. _To verify: when robocopy overwrites a file that carries `:Zone.Identifier`, does the stream survive, and does `start` on such an `.exe` show a security prompt?_
- **A2** — A helper finishes well within the sweep threshold.

## 6. Design (Phase 2)

### 6.1 Helper (US-1)

`buildApplyUpdateCmd()` loses exactly one line, the `powershell.exe … Unblock-File` call. Nothing else in the script moves: same arguments, same wait loop, same unconditional `:relaunch`, same `rmdir "%SRC%"`, still no self-delete. The PR #2 comment about the self-delete is rewritten so it no longer claims `%TEMP%` cleans itself, and points at the sweep instead. The file header (`zip-updater.ts:23-33`) drops the MOTW step and says why: the payload carries no MOTW (F1) and executables are stripped in-process on launch (F2).

### 6.2 One definition of the leftover names (D8)

`zip-updater.ts` exports the name builders and uses them where the files are created today:

```ts
export function updateStampName(version: string, pid: number): string   // wmux-update-<version>-<pid>
export function updateZipName(version: string, pid: number): string     // wmux-update-<version>-<pid>.zip
export function updateHelperName(pid: number): string                   // wmux-apply-update-<pid>.cmd
```

and the inverse, which is pure:

```ts
type LeftoverKind = 'helper' | 'extract-dir' | 'zip';
export function classifyUpdateLeftover(name: string): { kind: LeftoverKind; pid: number } | null
```

| Kind | Pattern | Expected type |
|---|---|---|
| `helper` | `^wmux-apply-update-(\d+)\.cmd$` | file |
| `zip` | `^wmux-update-([0-9A-Za-z.+-]+)-(\d+)\.zip$` | file |
| `extract-dir` | `^wmux-update-([0-9A-Za-z.+-]+)-(\d+)$` | directory |

Matching is case-sensitive and anchored. The captured PID must parse to a safe integer in `1..2³²−1`, or the classifier returns null; otherwise `process.kill` would throw `ERR_INVALID_ARG_TYPE` on an out-of-range number, which the sweep would treat as alive anyway, but the classifier is the place to say what a PID is. A version containing any other character is simply never swept: the failure mode of a too-narrow pattern is a kept file, never a removed one. A test pins the round trip for all three builders, so the builders and the patterns cannot drift apart.

### 6.3 The sweep (US-2, D6)

```ts
export interface SweepDeps {
  now: () => number;                       // Date.now
  isPidAlive: (pid: number) => boolean;    // see below
  maxAgeMs: number;                        // 60 * 60 * 1000
}
export interface SweepResult { removed: string[]; failed: { name: string; code: string }[] }
export async function sweepUpdateLeftovers(tmpDir: string, deps?: Partial<SweepDeps>): Promise<SweepResult>
```

**Pass 1 — collect.** Iterate `fs.promises.opendir(tmpDir)` (an iterator, so a `%TEMP%` with tens of thousands of entries is never held in one array). Keep only names that `classifyUpdateLeftover` accepts, and `lstat` each one. Build the set of **protected PIDs**: the PID of every helper-pattern entry that is fresh (age ≤ `maxAgeMs`, including negative) or whose `lstat` failed. Type is not checked here; a helper-named entry of any kind protects its PID, which only ever keeps more.

**Pass 2 — decide.** For each collected entry, stopping at the first rule that says keep:

1. `lstat` failed → keep.
2. `lstat` reports a symbolic link (libuv maps junctions to links) → keep.
3. Type does not match the kind (file vs directory) → keep.
4. `now − mtimeMs ≤ maxAgeMs` (includes negative) → keep.
5. Kind is `zip` or `extract-dir` and its PID is protected → keep.
6. `isPidAlive(pid)` → keep.
7. Remove with `fs.promises.rm(full, { recursive: kind === 'extract-dir', force: true })`. A throw goes into `failed` with its `code` (or `'UNKNOWN'`), and the loop continues.

Kept entries are not reported: nearly every launch keeps everything, and a log line per launch saying so is noise.

`isPidAlive` is `process.kill(pid, 0)`, which only tests that the process exists and sends nothing. It returns `true` when the call succeeds, `false` only on `ESRCH`, and `true` on anything else (`EPERM` means the process exists and belongs to someone else). A reused PID therefore reads as alive and keeps the entry. That costs one leftover for one more launch and nothing else.

Rule 5 is what closes F10. Without it, *Later* followed days afterwards by *Install and restart* gives an extract dir that is old and whose PID is dead while the helper is still using it. The new wmux would then delete it alongside the helper's own `rmdir`, and if the user started wmux by hand during the copy, it would delete the source under robocopy and leave a half-updated install.

### 6.4 Wiring (US-2.1–2.3, US-2.10)

In `index.ts`, inside the existing `if (app.isPackaged)` block (`index.ts:1145`), next to `initAutoUpdater()`:

```ts
if (process.platform === 'win32') {
  setTimeout(() => {
    sweepUpdateLeftovers(os.tmpdir())
      .then(({ removed, failed }) => {
        if (removed.length || failed.length) {
          logDiagnostic('update-sweep', {
            removed: removed.length,
            failed: failed.length,
            codes: [...new Set(failed.map((f) => f.code))],
          });
        }
      })
      .catch((err: Error) => logDiagnostic('update-sweep-error', { message: err?.message }));
  }, UPDATE_SWEEP_DELAY_MS).unref();
}
```

`UPDATE_SWEEP_DELAY_MS` is `60_000`, exported from `zip-updater.ts` beside the builders. The timer is `unref()`'d so it never keeps a quitting wmux alive. The sweep itself is not awaited, the same shape as `reconcileOrphanSessions` at `index.ts:1083`. This block sits in the `whenReady` handler after `if (!gotInstanceLock) return;` (`index.ts:993`), so a second launch that hands off to the running instance never sweeps. `os.tmpdir()` is the same resolution the creation side uses, so both read the same `TEMP`. The log carries counts and error codes (`EBUSY`, `EPERM`), not names: file names in `%TEMP%` are harmless, but the log is what users paste into issues, and codes are what tells an antivirus lock apart from a permissions problem.

### 6.5 Install that cannot strand the user (US-3, D7, D9)

`applyStagedPortableUpdate` becomes async and quits only once the helper is running:

```ts
export async function applyStagedPortableUpdate(staged: StagedZipUpdate): Promise<void> {
  if (!fs.existsSync(path.join(staged.extractDir, 'wmux.exe'))) {
    throw Object.assign(
      new Error('the downloaded update is no longer on disk — download it again'),
      { code: 'PAYLOAD_MISSING' },
    );
  }
  const helper = path.join(os.tmpdir(), updateHelperName(process.pid));
  fs.writeFileSync(helper, buildApplyUpdateCmd(), 'utf8');
  const child = spawn(cmd, buildHelperArgs(helper, [/* pid, src, dst, exe */]), {
    detached: true, stdio: 'ignore', windowsHide: true, windowsVerbatimArguments: true, // §6.6
  });
  await new Promise<void>((resolve, reject) => {
    child.once('spawn', resolve);
    child.on('error', reject); // `on`, not `once`: every late error stays handled
  });
  child.unref();
  app.quit();
}
```

The `'error'` listener stays attached after `'spawn'`, so a late error on the child is a no-op rather than an uncaught exception in main.

Both apply sites in `updater.ts` (the `ready` badge click, inside `setImmediate`, and the dialog's *Install and restart*) go through one local function:

```ts
async function applyStagedZipOrReset(staged: StagedZipUpdate): Promise<void> {
  if (applyingZip) return;          // a second click while the helper is starting
  applyingZip = true;               // stays set on success: wmux is quitting
  try {
    await applyStagedPortableUpdate(staged);
  } catch (err) {
    applyingZip = false;
    installPrompted = false;        // F11: the next update still asks
    zipApplyFailures += 1;          // reset whenever a new update is staged
    if ((err as { code?: string })?.code === 'PAYLOAD_MISSING') stagedZip = null;
    console.error('[updater] cannot apply staged zip update:', err);
    setState({ phase: 'error', message: String((err as Error)?.message ?? err) });
  }
}
```

`requestUpdateNow()` treats a click on the `error` badge with a still-staged zip as a retry. The retry goes back through the dialog, because that badge reads *Click to try again*, not *Restart*. It is also capped, so a failure that repeats (an antivirus blocking the helper every time) cannot turn every click into a dead one:

```ts
if (stagedZip && state.phase === 'ready') {
  const staged = stagedZip;
  setImmediate(() => { void applyStagedZipOrReset(staged); });
  return { handled: true };
}
if (stagedZip && state.phase === 'error') {
  if (zipApplyFailures >= MAX_ZIP_APPLY_ATTEMPTS) {   // 2: the first try and one retry
    return { handled: false, reason: 'install_failed', url: releasePageUrl(stagedZip.version) };
  }
  void promptToInstall(stagedZip.version);            // synchronously, and the phase stays `error`
  return { handled: true };
}
```

Two parts of that are load-bearing, and both were bugs in an earlier version of this branch:

- **The phase stays `error`, and the dialog starts without a `setImmediate`.** `promptToInstall` claims `installPrompted` before its first `await`, so a second quick click lands on that guard. Setting `ready` first, then deferring the dialog, let a second click take the `ready` branch and quit behind the open dialog.
- **`install_failed` carries the release page URL.** The renderer's fallback used to open only the release info cached from the notify-only poller, which may not have answered when the update was started from Help. `fallbackReleaseUrl` in `useUpdate.ts` prefers main's URL.

`stagedZip` is non-null in the `error` phase only after a failed install, since every download failure already clears it. So the outcomes are:

- **Payload gone:** `stagedZip` is null, the badge reads *Update failed: … download it again · Click to try again*, and the click goes down `requestPortableZipUpdate()` and downloads again.
- **Helper failed:** `stagedZip` is kept, the badge shows the failure, and the click shows the install dialog again. The payload guard runs again first, so a payload that vanished in the meantime still falls into the first case.
- **Helper failed twice:** the click opens the release page.

The guard is still a race: something could delete the payload in the gap between this `existsSync` and the helper's own check. That gap is the time `cmd.exe` takes to start, against the days F7 allows today.

### 6.6 Helper command line (D11)

```ts
export function buildHelperArgs(helper: string, args: string[]): string[]
// → ['/d', '/s', '/c', '""<helper>" "<pid>" "<src>" "<dst>" "<exe>""']
```

Spawned with `windowsVerbatimArguments: true`, so Node adds no quoting of its own. Throws if any piece contains `"`, or a `%…%` pair: quotes do not stop cmd expanding a defined variable, and `"C:\x\%OS%\y"` was measured arriving as `C:\x\Windows_NT\y`. A lone `%` passes through unchanged and is allowed. From `applyStagedPortableUpdate` a throw is a rejection before quit, like every other failure in §6.5.
